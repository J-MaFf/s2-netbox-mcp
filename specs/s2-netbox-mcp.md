# Spec: S2 NetBox MCP Server (Read-Only)

## Goal
Build a local MCP server that exposes read-only S2 NetBox NBAPI operations (persons/credentials, access levels, portals/readers, events/history) as Claude-callable tools, so NetBox data can be queried conversationally instead of hand-built XML/HTTP calls.

## Context
- The target system is LenelS2's **S2 NetBox** physical access-control appliance — not the unrelated open-source "NetBox" DCIM/IPAM tool (netboxlabs.com), which already has its own MCP server that has nothing to do with this project.
- Its integration surface is the **NBAPI**: XML-over-HTTP, documented in "Web-Based API for S2 NetBox and S2 Global" (LenelS2, February 2020, doc #API-UG-14; current with S2 NetBox Release 5.0 / S2 Global 2.0.12). The Overview, Calling the API, Authentication, and full Command Reference table of contents were reviewed directly from the official PDF for this spec.
- Verified (checked the official PDF): request/response structure, endpoint paths, both auth modes, XML uppercase-*element*-tag requirement (attribute values like `sessionid=`/`name=`/`num=`/`dateformat=` stay lowercase, per the documented examples — the doc's "all XML tags must be uppercase" note refers to element names, not attributes), error model (`APIERROR` vs `CODE`/`FAIL`/`ERRMSG`/`NOT FOUND`), and the full list of ~90 documented commands with page numbers.
- Verified (checked the official PDF's Command Reference section directly, in detail, for every command this spec uses): exact PARAMS and response field names for `Login`, `Logout`, `GetAPIVersion`, `GetPerson`, `SearchPersonData`, `GetCardAccessDetails`, `GetCardFormats`, `GetAccessLevel(s)`, `GetAccessLevelGroup(s)`, `GetPortals`, `GetReader(s)`, `GetEventHistory`, `ListEvents`, `GetAccessHistory`. Notably: **there is no command named `GetPortal` (singular)** — only `GetPortals` exists, and its only parameter is `STARTFROMKEY` (pagination cursor); it cannot be filtered to a single portal. `GetReader` (singular) does exist and takes a required `READERKEY`. The PDF is saved locally at `C:\Users\jmaffiola\.claude\projects\C--Users-jmaffiola-Documents-Tasks\9b02c63b-5b70-42ba-8ef1-bd9e89371a6e\tool-results\webfetch-1789396815900-v6cg0d.pdf` (an image-rendered PDF; printed page label + 5 = the Read tool's page index, verified stable through the whole Command Reference section) for anyone who needs to re-check a field name against the primary source.
- Verified (web search, 2026-09-14): no existing MCP server wraps the S2 NetBox NBAPI. This is a from-scratch build.
- **Endpoint (verified live, 2026-09-14, against the user's controller running NetBox 6.2.0):** on NetBox 6.x the NBAPI is served at `http(s)://<host>[:port]/nbws/goforms/nbapi`. The 2020 doc's path `/goforms/nbapi` returns **HTTP 410 Gone** on 6.2.0 for every method and body — it is deliberately deregistered, not disabled. Corroborated by two independent modern integrations that use the `/nbws/goforms/nbapi` path: the Go client `github.com/gemini-oss/rego/pkg/lenel_s2` (constant `"%s/nbws/goforms/nbapi"`, published 2025) and Maptician's LenelS2 NetBox integration doc (`https://help.maptician.com/presence/lenels2-netbox-integration-overview-and-network-requirements`). Everything else about the protocol (XML envelope, commands, field names, error model) is unchanged from the 2020 doc — verified by the live round trip below. (The `/appd/nbapi` and `/appdevent/nbapi/event` endpoints are for event triggering and event streaming, both out of scope for v1 — see below; whether they also moved under `/nbws/` is unverified and irrelevant to v1.)
- **Verified live round trip (2026-09-14, session-login mode, `/nbws/goforms/nbapi`):** `Login` → `<NETBOX sessionid="…"><RESPONSE command="Login" num="1"><CODE>SUCCESS</CODE></RESPONSE></NETBOX>` (64-character sessionid, no cookie set — the sessionid attribute is the only session carrier); `GetAPIVersion` → `<DETAILS><APIVERSION>6.2.0</APIVERSION></DETAILS>`; `GetAccessLevels`, `GetPortals`, `GetReaders`, `GetCardFormats` → `SUCCESS` with DETAILS matching the field names in the Command reference section below; `Logout` → `<NETBOX><RESPONSE command="Logout" num="1"><CODE>SUCCESS</CODE></RESPONSE></NETBOX>` (note: the Logout response's `<NETBOX>` carries **no** sessionid attribute — parsing must not require it). Every response was HTTP 200 with `Content-Type: text/xml`, including APIERROR responses.
- **Auth precondition (verified live):** v1 targets **session-login authentication only**. This requires, on the controller at *Configuration → Site Settings → Network Controller → Data Integration*, all of: **Enable V2** ☑ (the checkbox the 6.x UI shows in place of the 2020 doc's "Enabled"), **Use Authentication** ☑, and **Use login username/password for authentication (requires setup privilege)** ☑. The observed failure mode when that third box is unchecked (controller then expects MAC auth) is subtle and must be documented in the README: `Login` still returns `SUCCESS` with a sessionid, but **every** subsequent command — including `Logout` and `PingApp` — returns `<APIERROR>5</APIERROR>`, and passing the sessionid as a cookie, as a `<SESSIONID>` element, or alongside a bogus `<MAC>` does not help. Only ticking the checkbox fixed it (verified: same credentials, same code, before/after). The API user must hold a role with NBAPI read access (the 2020 doc's "Creating User Roles for API" section).
- The documented MAC-authentication alternative (`<MAC>` element, no login step, requires *Use Authentication* ☑ and *Use login username/password* ☐, plus the 8-character "SHA Secret" and a monotonically increasing sequence number) is out of scope for v1 and currently **not implementable from public information**: the MAC is `RAN1(5 digits) + RAN2(5 digits) + SEQ(10 digits) + SHA-1(chksum(msg) || secret || seed)`, but the `chksum` step is never specified in the 2020 LenelS2 doc, the 2007 IEI eMerge ancestor doc (`https://www.chicopeeelectronics.com/Downloads/eMerge%20API-DataExchangev2_5.pdf`, which prints only the `generate_mac` C signature, not its body), or any public client (the Ruby gem `Teamsquare/s2_netbox` explicitly does not implement it; `gemini-oss/rego` uses session login only). The reference C implementation lives behind LenelS2 Support Central, which the user does not have access to.

### Command reference (verified against the primary source — authoritative, use these exact field names)
Field names below are copied from the official NBAPI Command Reference (see Context). A tool's PARAMS must use exactly these element names inside `<PARAMS>`; response parsing must expect exactly these DETAILS field names. Do not invent, rename, or guess a field name not listed here.

Response envelope (applies to every command, not just Login): every response is wrapped in `<NETBOX sessionid="...">`, verified directly from the doc's general "XML Responses" section (not just the Login-specific text below) — `NETBOX` is documented as "the outermost element of the response," carrying the `sessionid` attribute for the logged-in session, with a nested `<RESPONSE command="..." num="1"><CODE>...</CODE><DETAILS>...</DETAILS></RESPONSE>`. `<NETBOX-API>` is the *request* wrapper only; `<NETBOX>` is always the *response* wrapper.

Items marked **[live 6.2.0]** were additionally confirmed byte-for-byte against the user's NetBox 6.2.0 controller on 2026-09-14; the rest are doc-verified only.

- **Login** — PARAMS: `USERNAME` (required), `PASSWORD` (required). On SUCCESS there is no sessionid field inside the response body — the session id is the `sessionid` *attribute* on the outer `<NETBOX>` response element itself, to be reused as the `sessionid` attribute on every subsequent `<NETBOX-API>` call. On FAIL: `APIERROR` 5. **[live 6.2.0]**: `<NETBOX sessionid="<64 chars>"><RESPONSE command="Login" num="1"><CODE>SUCCESS</CODE></RESPONSE></NETBOX>`; no `Set-Cookie` header.
- **Logout** — PARAMS: none. Response: `CODE` only. **[live 6.2.0]**: `<NETBOX><RESPONSE command="Logout" num="1"><CODE>SUCCESS</CODE></RESPONSE></NETBOX>` — the outer `<NETBOX>` has no `sessionid` attribute on this response.
- **GetAPIVersion** — PARAMS: none. Response: `APIVERSION`. **[live 6.2.0]**: `<DETAILS><APIVERSION>6.2.0</APIVERSION></DETAILS>`.
- **GetPerson** — PARAMS: `PERSONID` (required), `ALLPARTITIONS` (optional), `ACCESSLEVELDETAILS` (optional), `WANTCREDENTIALID` (optional). Response: `PERSONID`, `FIRSTNAME`, `LASTNAME`, `MIDDLENAME`, `EXPDATE`, `ACTDATE`, `NOTES`, `UDF1`–`UDF20`, `DELETED`, `ACCESSLEVELS` (list of `ACCESSLEVEL`), `ACCESSCARDS` (list of `ACCESSCARD`: `ENCODEDNUM`, `HOTSTAMP`, `CREDENTIALID`, `CARDFORMAT`, `DISABLED`, `CARDSTATUS`, `CARDEXPDATE`), `PICTUREURL`.
- **SearchPersonData** — PARAMS (all optional filters; omit all to return every record): `PERSONID`, `LASTNAME`, `FIRSTNAME`, `MIDDLENAME`, `UDF1`–`UDF20`, `HOTSTAMP`, `WANTCREDENTIALID`, `ACCESSLEVEL`, `OLDESTLASTMOD`, `NEWESTLASTMOD`, `DELETED` (`ALL`/`TRUE`/`FALSE`), `ALLPARTITIONS`, `CASEINSENSITIVE`, `WILDCARDSEARCH`, `ACCESSLEVELDETAILS`, `RAWCARDNUMBER`. Response: `PEOPLE` (list of `PERSON`, same shape as GetPerson plus `PIN`/`LASTEDIT`/contact fields/`VEHICLES`), `NEXTKEY`.
- **GetCardAccessDetails** — PARAMS: `ENCODEDNUM` (required), `CARDFORMAT` (required), `MAXRECORDS` (optional), `OLDESTDTTM` (optional). Response: `PersonID`, `Disabled`, `expdate`, `Accesses` (list of `Access`: `DTTM`, `NODEDTTM`, `TYPE`, `PORTALNAME`, `REASON`, `PORTALKEY`, `READERKEY`, `LOGID`), `NEXTLOGID`.
- **GetCardFormats** — PARAMS: none. Response: `CARDFORMATS` (list of `CARDFORMAT`). **[live 6.2.0]**: `<DETAILS><CARDFORMATS><CARDFORMAT>26 bit Wiegand</CARDFORMAT>…</CARDFORMATS></DETAILS>` (14 formats on the test controller, plain-text names).
- **GetAccessLevel** — PARAMS: `ACCESSLEVELKEY` (required). Response: `ACCESSLEVELNAME`, `ACCESSLEVELDESCRIPTION`, `READERGROUPKEY`, `TIMESPECGROUPKEY`, `THREATLEVELGROUPKEY`.
- **GetAccessLevels** — PARAMS: `STARTFROMKEY` (optional), `STARTFROMNAME` (optional), `WANTKEY` (optional). Response: `ACCESSLEVELS` (list of `ACCESSLEVEL`), `NEXTKEY`, `NEXTNAME`. **[live 6.2.0]** with no PARAMS: `<DETAILS><ACCESSLEVELS><ACCESSLEVEL>ALL ACCESS</ACCESSLEVEL>…</ACCESSLEVELS><NEXTNAME></NEXTNAME></DETAILS>` — each `ACCESSLEVEL` is a bare name string (no key) unless `WANTKEY` is sent; `NEXTNAME` is present but empty on the last page and `NEXTKEY` is absent. Parsers must treat an empty `NEXTNAME`/`NEXTKEY` as "no more pages".
- **GetAccessLevelGroup** — PARAMS: `ACCESSLEVELGROUPKEY` (required). Response: `ACCESSLEVELGROUPKEY`, `NAME`, `DESCRIPTION`, `ACCESSLEVELS` (list of `ACCESSLEVEL`: `KEY`, `NAME`).
- **GetAccessLevelGroups** — PARAMS: `STARTFROMKEY` (optional). Response: `ACCESSLEVELGROUPS` (list of `ACCESSLEVELGROUP`: `KEY`, `NAME`), `NEXTKEY`, `NEXTNAME`. **[live 6.2.0]**: on a controller with zero Access Level Groups configured (access levels present but not grouped), both `GetAccessLevelGroups` and `GetAccessLevelGroup` return `<CODE>FAIL</CODE><DETAILS><ERRMSG>NOT FOUND</ERRMSG></DETAILS>` rather than an empty `ACCESSLEVELGROUPS` list or the documented `<CODE>NOT FOUND</CODE>` — a controller-specific "empty collection" signal, not a client defect. `scripts/live-check.ts` treats a bare `ERRMSG="NOT FOUND"` on these two commands as an accepted no-data outcome for smoke-test purposes; the NBAPI client itself still surfaces it as a normal `<CODE>FAIL</CODE>` tool error per R8 — this is a live-check harness accommodation, not a change to R8/R9's documented error semantics.
- **GetPortals** — PARAMS: `STARTFROMKEY` (optional pagination cursor) — this is the *only* parameter; there is no single-portal filter. Response: `PORTALS` (list of `PORTAL`: `NAME`, `PORTALKEY`, `READERS` (list of `READER`: `READERKEY`, `NAME`, `DESCRIPTION`, `PORTALORDER`)), `NEXTKEY`. **[live 6.2.0]**: `<PORTAL><PORTALKEY>1</PORTALKEY><NAME>…</NAME><READERS><READER><READERKEY>1</READERKEY><NAME>…</NAME><PORTALORDER>1</PORTALORDER></READER></READERS></PORTAL>` — nested readers omit `DESCRIPTION` here (it is returned by `GetReaders`/`GetReader` instead); element order is `PORTALKEY` before `NAME`. Parsers must not require `DESCRIPTION` on nested readers.
- **GetReader** — PARAMS: `READERKEY` (required). Response: `READER` (`READERKEY`, `NAME`, `DESCRIPTION`).
- **GetReaders** — PARAMS: `STARTFROMKEY` (optional) — no portal-id or other filter. Response: `READERS` (list of `READER`: `READERKEY`, `NAME`, `DESCRIPTION`). **[live 6.2.0]**: `<READERS><READER><READERKEY>1</READERKEY><NAME>…</NAME><DESCRIPTION>…</DESCRIPTION></READER>…` — reader keys are not contiguous (1, 4, 7, 10, 13 … on the test controller); never assume sequential keys.
- **GetEventHistory** — PARAMS: `EVENTNAME` (optional), `STARTDTTM` (optional), `ENDDTTM` (optional), `NEXTKEY` (optional, pagination continuation). Response: CSV-formatted event list (`LogID`, `Time`, `EventName`, `Type`, `Reason`), `NEXTKEY`.
- **ListEvents** — PARAMS: none. Response: `EVENTS` (list of `EVENT`: `NAME`, `PARTITIONID`, `ACTIONS`).
- **GetAccessHistory** — PARAMS (all optional): `STARTLOGID`, `AFTERLOGID`, `ORDER`, `MAXRECORDS`, `ENCODEDNUM`, `HOTSTAMP`, `CARDFORMAT`, `OLDESTDTTM`, `NEWESTDTTM`. Response: `ACCESSES` (list of `ACCESS`: `LOGID`, `PERSONID`, `READER`, `DTTM`, `NODEDTTM`, `TYPE`, `REASON`, `READERKEY`, `PORTALKEY`), `NEXTLOGID`.

## Out of scope
- Any write/control command, including but not limited to: `AddPerson`, `ModifyPerson`, `RemovePerson`, `Add/Modify/DeleteAccessLevel(Group)`, `LockPortal`, `UnlockPortal`, `MomentaryUnlockPortal`, `Activate/DeactivateOutput`, `Set/Add/Modify/RemoveThreatLevel(Group)`, `TriggerEvent`, `Add/Modify/DeleteHoliday`, `Add/Modify/DeleteTimeSpec(Group)`, `Add/Modify/RemoveCredential`, `AddPartition`, `SwitchPartition`, `InsertActivity`, `ModifyUDFListItems`.
- Photo ID handling (`GetPicture` and photo upload) — separate binary/Base64 concern, deferred.
- `StreamEvents` and the `/appdevent/nbapi/event` push feed — architecturally a persistent connection rather than request/response; deferred to a future version.
- MAC-based authentication — session-login only for v1. If a later version adds it, the blocking gap is the unspecified `chksum(msg)` step of `generate_mac` (see Context); the design must not be started until either the vendor's reference C code or a known-good (message, secret, seq, MAC) tuple is obtained.
- Supporting pre-6.x controllers beyond the `NETBOX_API_PATH` override in R20 (no 5.x controller is available to test against).
- S2 Global's API variant — this spec targets S2 NetBox only.
- Any GUI, dashboard, or interface beyond the MCP tool surface.
- Publishing/packaging the server (e.g. to npm) — local use only for now.

## Constraints
- Language/runtime: TypeScript on Node.js, using `@modelcontextprotocol/sdk`.
- Transport: stdio (how Claude Code registers local MCP servers).
- No secrets committed to the repo; `.env` is gitignored; `.env.example` contains placeholders only.
- Must run on Windows 11 natively, without requiring WSL.
- Must follow this user's global `CLAUDE.md` secrets-hygiene and injection-defense rules.
- XML element names must be uppercase per the NBAPI spec; attribute names/values stay lowercase as documented (see R2).
- Optional `NETBOX_ALLOW_INSECURE_TLS` must default to `false`/unset (reject self-signed certs by default); enabling it is an explicit opt-in, not a silent fallback.
- The default API path is `/nbws/goforms/nbapi` (R20). The client must never fall back to `/goforms/nbapi` automatically on a 410 — it surfaces the error (R21) and leaves the choice to the operator via `NETBOX_API_PATH`.
- Live checks are only ever run through `npm run test:live` with credentials from the environment/.env; no test fixture, snapshot, or README example may contain the real controller host, username, or password.

## Acceptance rubric
- C1 (from R1): PASS iff the server starts via the documented command and responds to `list_tools` without error.
- C2 (from R2): PASS iff a captured request for at least one tool call matches the documented `NETBOX-API`/`COMMAND`/`PARAMS` XML structure, with element names uppercase and attribute names/values (`sessionid`, `name`, `num`, `dateformat`) lowercase exactly as documented.
- C3 (from R3): PASS iff starting the server with a required env var unset produces a one-line actionable error and a non-zero exit code, with no stack trace printed.
- C4 (from R4): PASS iff two sequential tool calls within one server run produce exactly one `Login` request.
- C5 (from R5): PASS iff a simulated session-expiry causes exactly one automatic re-login and the original call still succeeds.
- C6 (from R6): PASS iff sending SIGINT or SIGTERM to a running server triggers a `Logout` request before the process exits.
- C7 (from R7): PASS iff each of the six documented `APIERROR` codes, when simulated, surfaces as an MCP tool error containing its documented description.
- C8 (from R8): PASS iff a simulated `FAIL` response carrying an `ERRMSG` surfaces as an MCP tool error containing that `ERRMSG` text verbatim.
- C9 (from R9): PASS iff a `NOT FOUND` response returns a normal (non-error) tool result stating not-found.
- C10 (from R10): PASS iff a grep of the source tree for NBAPI command-name literals used as a `COMMAND name=` value turns up only the 17 commands listed in R10, with no write/control verb among them and no non-existent command (e.g. no literal `GetPortal`).
- C11 (from R11–R17): PASS iff `npm run test:live`, run with the project's real `.env` against the live 6.2.0 controller, reports PASS for all 15 commands backing the 15 tools (`check_connection`, `get_person`, `search_person_data`, `get_card_access_details`, `get_card_formats`, `get_access_level`, `get_access_levels`, `get_access_level_group`, `get_access_level_groups`, `get_portals`, `get_reader`, `get_readers`, `get_event_history`, `list_events`, `get_access_history`) and exits 0, and the `check_connection` line shows `6.2.0`. - C12 (from R18): PASS iff each tool's registered input schema's parameter names and required/optional status match exactly the "Command reference (verified against the primary source)" section's list for that command — no invented, renamed, or guessed field name anywhere.
- C13 (from R19): PASS iff a grep for the `NETBOX_PASSWORD` usage across `src/` and `test/` shows it only ever flows into the login request body, never into a log/console/error call.
- C14 (from R20): PASS iff a captured request URL with `NETBOX_API_PATH` unset ends in `/nbws/goforms/nbapi`, a config test shows an override is honoured, and no file in `src/`, `README.md`, or `.env.example` presents `/goforms/nbapi` as the default.
- C15 (from R21): PASS iff a mocked HTTP 410 surfaces as a tool error naming the status, the request path, and `NETBOX_API_PATH`, and a mocked HTTP 500 surfaces as a tool error naming the status and path, with neither containing credentials.
